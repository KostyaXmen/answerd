# Идеи

Здесь собрано то, что обсуждалось или проверялось, но в код не вошло. У каждой идеи одинаковый набор полей.

Возможные статусы: **не реализовано**, **частично реализовано**, **проверено и отклонено**, **прототип откачен**.

---

## 1. Локальный OCR: скриншот → текст

**Идея.** Распознавать текст на скриншоте локально и отдавать в текстовый конвейер вместо vision-запроса.

**Суть.**
- `spectacle -o` сохраняет снимок в файл.
- `tesseract` распознаёт текст (`rus+eng`).
- Текст уходит в `AskText`; vision используется только как fallback.

**Что проверено.**
- `tesseract` 5.5.3 установлен, но доступны только `afr` и `osd` — без `rus`/`eng` бесполезен.
- Пакеты: `tesseract-data-rus`, `tesseract-data-eng` (Arch/Manjaro) или `tesseract-ocr-rus`, `tesseract-ocr-eng` (Debian/Ubuntu).
- Команда для проверки: `tesseract shot.png stdout -l rus+eng --psm 6`.
- Качество падает на фото экрана, наклонённых снимках и формулах; препроцессинг (увеличение, бинаризация) помогает.

**Почему не сделано.**
- Не установлены языковые пакеты.
- Для экзаменационных скриншотов vision уже работает достаточно хорошо.
- Нужен fallback и проверка качества, иначе можно ухудшить результат.

**Что нужно.**
- Поставить языковые пакеты `rus` и `eng`.
- Добавить шаг OCR перед `AskText`.
- Отправлять в vision, если OCR вернул мало текста или в нём есть формулы/схемы.
- Замерять качество на реальных скриншотах.

**Конфиг.** `ocr`, `ocr_lang`, `ocr_min_chars`, `ocr_fallback_vision`.

**Риски.**
- OCR ошибается на формулах, таблицах и цветном тексте.
- Появляется внешняя зависимость `tesseract` + языковые модели.

**Статус.** не реализовано.

## 2. Локальная база ответов (`questions.txt`)

**Идея.** Искать вопрос в готовом банке ответов и идти в API только при промахе.

**Суть.**
- Конвертер разбирает `questions.txt` в `answers.jsonl`.
- Поиск: точное совпадение по нормализованному тексту → нечёткий поиск → fallback в DeepSeek.
- Правильный вариант сопоставляется с вариантами на экране по тексту.

**Что проверено.**
- Файл: 22 033 строки, 2.2 МБ, ~2 900 вопросов из нескольких источников (банк в стиле PMBOK + «Книги 1–4»).
- 6 вариантов заголовков: `Вопрос №N.`, `Книга … Вопрос N:`, `Книга … Страница N. <вопрос>`, `N. Страница N.`, `N. Стр. N`, «висячие» метаданные.
- 4 способа пометки ответа: `+` перед вариантом, `Ответ: A, D, E`, свободный текст ответа, кириллические `а)–г)`.
- Встречаются переносы вопросов и вариантов, склеенные заголовки, 451 NBSP, 664 табуляции, CRLF.
- ~500 нормализованных текстов вопросов повторяются; ~400 вопросов содержат только текст ответа без вариантов.

**Почему не сделано.**
- Файл не типизирован; парсер требует нескольких итераций по отчёту.
- База полезна только если экзамен действительно составлен из этого банка.
- Вопросы на экзамене могут встречаться один раз — кэш ответов не помогает, нужен именно поиск по банку.

**Что нужно.**
- Конвертер с отчётом по нераспознанным блокам.
- Канонический `answers.jsonl`: `q`, `options`, `answer_text`, `answer_idx`.
- Exact hash → fuzzy (шинглы/BM25) → API.
- Сопоставление правильного варианта по тексту, а не по позиции.
- Для скриншотов предварительно нужен OCR (см. идею 1).

**Конфиг.** `answers_file`, `answers_min_score`, `answers_writeback`.

**Риски.**
- Ошибки и устаревшие данные в банке.
- Конфликтующие дубликаты: при разных ответах лучше идти в API.
- SQLite + FTS5 может понадобиться, если база вырастет.

**Статус.** не реализовано.

## 3. Консенсус N параллельных запросов

**Идея.** Спрашивать модель N раз параллельно и возвращать самый частый ответ.

**Суть.**
- N запросов с разными температурами (`base + i*step`).
- Ответы нормализуются и подсчитываются.
- Ничья или недобор кворума — ошибка, а не догадка.

**Что проверено.**
- Прототип на 5 запросах с температурами 0.6–1.0 был реализован и откачен.
- При `temperature: 0` запросы почти детерминированы — голосование бесполезно.
- Параллельность сохраняет латентность на уровне одного запроса, но цена — ×N.
- «Погрешность 10%» не гарантируется: выигрыш зависит от одиночной точности и независимости ошибок.
- Ничья `01:2 02:2` должна давать ошибку.

**Почему не сделано.**
- Откачено по вашему запросу.
- Нужна ненулевая температура, иначе нет смысла.
- ×N стоимость и нагрузка на rate limit; для vision — ×N загрузка картинок.

**Что нужно.**
- N = 3–5, температура 0.6–0.8, общий промпт и картинка.
- Подсчёт голосов, обработка ничьей и кворума.
- Ограничение одновременности, чтобы не ловить 429.

**Конфиг.** `consensus_n`, `consensus_temperature`, `consensus_temperature_step`, `consensus_quorum`.

**Риски.**
- Рост стоимости.
- Ошибки модели могут быть коррелированы — голосование не поможет.
- При нескольких правильных вариантах возможны ничьи.

**Статус.** прототип откачен.

## 4. Сжатие изображений перед отправкой

**Идея.** Уменьшать картинку до отправки: палитра PNG и/или даунскейл.

**Суть.**
- Декодировать PNG, при необходимости уменьшить ширину.
- Квантовать цвета в палитру (median-cut).
- Отправлять палитровый PNG вместо полноразмерного.

**Что проверено.**
- На 4K-скриншоте (3840×1243, исходник 1.62 МБ):

  | Вариант | base64 | prompt_tokens | Латентность API |
  |---|---|---|---|
  | оригинал | 2.16 МБ | 1040 | 3564 мс |
  | 2560 + 32 цвета | 190 КБ | 1040 | 2250 мс |
  | 1920 + 32 цвета | 116 КБ | 737 | 1530 мс |
  | 1600 + 32 цвета | 89 КБ | 552 | 1646 мс |

- Палитра 32 цвета сохраняет текст резким; JPEG даёт ringing вокруг букв.
- Grayscale сжимается хуже палитры — не нужен.
- Ниже 1280 мелкий текст становится нечитаемым.
- Сервер, похоже, ограничивает картинку ~1040 токенами: 4K и 2560 дают одинаковые токены, только 1920/1600 снижают.
- ImageMagick тратит 1.9–2.8 с на кадр — это съедает выигрыш.

**Почему не сделано.**
- Нужна быстрая Go-реализация: median-cut + билинейный ресайз, ориентировочно 0.2–0.6 с.
- Не выбран итоговый пресет (ширина, число цветов).

**Что нужно.**
- Реализовать сжатие на stdlib.
- Замерять полный цикл «сжатие + запрос» до/после.
- Сравнить ответы модели на оригинале и сжатой картинке.

**Конфиг.** `image_max_width`, `image_format`, `image_colors`.

**Риски.**
- Потеря мелкого текста при сильном даунскейле.
- Бандинг на градиентах при малом числе цветов.
- CPU-затраты на каждый запрос.

**Статус.** не реализовано.

## 5. HTTP-сжатие тела запроса

**Идея.** Сжимать JSON-тело запроса через `Content-Encoding: gzip`.

**Суть.**
- Сериализовать запрос, сжать gzip, отправить с заголовком `Content-Encoding: gzip`.

**Что проверено.**
- DeepSeek API не поддерживает сжатые тела: возвращает `400 Failed to parse the request body as JSON`.
- Даже если бы поддерживал, выигрыш мал: `gzip(base64(PNG))` даёт лишь ~25% (2.16 МБ → 1.61 МБ), так как PNG уже сжат.
- Go и так автоматически распаковывает gzip-ответы.

**Почему не сделано.**
- API не поддерживает `Content-Encoding`; включать нельзя — сломает все запросы.

**Что нужно.**
- Ничего; идея закрыта.

**Конфиг.** —

**Риски.**
- При включении — ошибки 400 на каждом запросе.

**Статус.** проверено и отклонено.
